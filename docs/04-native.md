# 04 · Rust applets and services

A Rust applet is the same store as a Flutter one, in the `vrx` crate
(`rust/sdk`). It runs as the same kind of systemd unit, with the same
grants, and reaches the same `io.vrx.Host`. Use Rust where there is no
screen, or where the work is close to the kernel; use Flutter for anything
a person looks at.

## The store

```rust
use vrx::{applet_main, prelude::*};

impl Applet for Hello {
    type State = i32;
    type Action = Action;
    type View = View;
    fn initial() -> i32 { 0 }
    fn boot_action() -> Action { Action::Start }
    fn reduce(&mut self, state: &i32, action: &Action) -> View { /* pure */ }
    fn effects(&mut self, state: &i32, action: &Action) -> Vec<Effect> { vec![] }
}
```

`applet_main(applet)` (generated by `vrx new --rust`) seeds the store,
renders the boot view, tells systemd `READY=1` (the unit's 5 s start
budget), and pings the watchdog from a thread only while the action loop
is healthy: idle, or busy for less than half the interval. A reducer stuck
past that stops the pings and systemd restarts the applet, the verdict a
hung UI loop gets (`rust/sdk/src/service.rs`). `StoreHarness` runs the
model in a test and fails a reduce over 2 ms.
`cargo run -p vrx --example hello` proves the whole path on the Mac.

## Console applets

A Rust applet with a screen draws through the console kit
(`rust/sdk/src/kit.rs`): a `Screen` of `Row`s (`text_title`, `text_body`,
`text_row`, `button`). Its layout test calls
`vrx::layout::assert_clean_layout(&screen)` for each screen in
`tests/layout.rs`, which computes the console grid from each panel's
millimetres in the shared display table and fails a row wider than the
grid or a word longer than a line. With `[applet.command] enabled = true`
the applet is also a shell pipeline stage: each line on stdin is a JSON
action and each render goes to stdout. `applets/console` is the example;
it ships in no image.

## Services

A service has no screen (`kind = "service"` in the manifest): vrxhost
starts and supervises it and never opens it (`Push` answers
`NotOpenable`). It needs no layout test, may not be a tile or declare
routes, and is never frozen. `applets/stt` is the example: resident from
boot, it handles `sys.stt.listen`, records through ALSA (the `audio`
grant), has the local whisper server transcribe through
`/run/vrx-ml/stt.sock` (the `ml` grant), and answers `sys.stt.heard`.

## IPC

`vrx::ipc` wraps the bridge (`03-ipc.md`):

| Call | What |
|---|---|
| `intent_send(name, payload)` | send an intent; the result is the verdict |
| `Listener` | hold `Listen` and receive intents, routes and channels (`Delivery`) |
| `answer(id, handled)` | answer a told intent within its 100 ms |
| `Channel` | a stream end vrxhost handed over |
| `BufferQueue` | buffers by index over a channel (`rust/sdk/src/bufq.rs`) |

`vrx::ipc::host_socket()` is `/run/vrx/io.vrx.Host`. Everything is
synchronous Rust on purpose: an applet's loop is one thread of actions,
and no call blocks it for longer than a reduce may take.

## The rules

Rust applets are under the same scan as Flutter ones (`thread::sleep(` is
refused; nothing polls without `// poll-ok: <reason>`), the workspace's
rules (no `unwrap`, `expect`, `panic!`, `print*` outside tests; no
`unsafe`), and the gate's fmt, clippy `-D warnings` and tests, chosen by
impact. AGENTS.md has the full list.
